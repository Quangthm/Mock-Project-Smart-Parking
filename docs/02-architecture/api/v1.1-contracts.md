## Route and schema authority

Retain the established integration route families `/api/auth/register/driver`, `/api/auth/register/owner`, `/api/users`, `/api/owner-applications`, `/api/vehicles` and `/api/parking-lots`. Earlier design spellings `/driver-register`, `/owner-register`, separate `/api/admin/.../approve` and `/reject`, and the separate registration-status lookup are superseded design proposals, not additional supported aliases. No new status endpoint is required merely to duplicate approval email and safe login failure communication (D07).

The known `success/data` success envelope and `success/code/message` business-error envelope are existing integration conventions. Earlier claims that every endpoint strictly implements one RFC problem-details schema were unsupported: framework binding/auth responses differ. V11-DES-03 below must agree the final success/error and token-delivery contract, including new status reasons. Retained route references do not prove implementation compliance. No client must infer access from a response label or assumed DB enum.

## Authentication and normal login

| Operation | Established method/path | Input and authorized output |
|---|---|---|
| Password login | `POST /api/auth/login` | Existing `email` field accepts email/phone plus `password`; validate credentials and current access, then required MFA. Completed login returns necessary tokens only. |
| Request primary login OTP | `POST /api/auth/otp/request` | `contact`; only a verified bound channel is eligible. Challenge metadata is not a normal session. |
| Complete OTP primary proof | `POST /api/auth/otp/login` | Existing `challengeId`, `code`; enabled TOTP requires the restricted second-stage flow before normal tokens. Final challenge payload and route agreement pending V11-DES-03. |
| Account/profile retrieval | `GET /api/auth/me` | Current full session; return only authorized identity/profile data. Onboarding details, if needed, are retrieved here or through an agreed authorized resource, never unconditionally on login. |
| Refresh | `POST /api/auth/refresh` | Existing `refreshToken`; rotate with atomic reuse protection, current account/security checks and original absolute deadline. |
| Logout | `POST /api/auth/logout` | Current bearer and matching refresh/session; revoke current session. Other sessions remain independent except explicit all-session revocation actions. |
| TOTP setup/enable | `POST /api/auth/mfa/setup`, `POST /api/auth/mfa/enable` | Existing entry points; full enrollment, backup-code, disable and replacement contracts follow the canonical recovery document. V11-DES-03 must reconcile legacy one-step OTP+TOTP behavior. |

Access lifetime remains **15 minutes**; refresh has **7-day absolute lifetime** and **24-hour inactivity limit**. Rotation cannot extend the original absolute maximum. Registration OTP remains six digits, five-minute validity, sixty-second resend cooldown and **three failures → fifteen-minute lock**. Resend preserves failed-attempt/lock protections and invalidates the old code. Optional TOTP applies to all four roles; once enabled it is mandatory after primary proof. Password or independently verified email/phone may be primary login; no trusted-device bypass. Current session/security version and lot grants are enforced at resource access, including subscriptions.

Illustrative completed-login shape using the retained envelope, subject to V11-DES-03 token delivery agreement; `expiresIn` reflects the approved lifetime, not the former snapshot defaults:

```json
{
  "success": true,
  "data": {
    "accessToken": "<issued-access-token>",
    "refreshToken": "<issued-refresh-token>",
    "tokenType": "Bearer",
    "expiresIn": 900
  }
}
```

There is no `user`, profile or `onboardingComplete` field in this normal-success example. Required MFA challenge data remains a separate incomplete-authentication result. Failures remain safe, standardized and actionable: invalid credentials, unverified contact, pending review, rejection with safe explanation, initial provisioning pending/failed, independent lock/disable, and factor/recovery requirement must remain distinguishable where authorized. Existing reason names such as `AUTH_FAILED`, `CONTACT_UNVERIFIED`, `ACCOUNT_PENDING_APPROVAL`, `ACCOUNT_REJECTED` and `MFA_REQUIRED` are integration references; new provisioning reason names and HTTP/envelope details are design-pending V11-DES-03. Account-specific details require sufficient credential validation; never reveal raw exceptions, secrets or unreviewed internal notes.

Pending Partner setup/verification credentials have only the authorized application/purpose scope. An application ID or unverified email is not authorization; they cannot call ordinary APIs or subscribe to private channels. Credential TTL, delivery, storage, rotation and secure recovery remain V11-DES-03, not the normal access-token lifetime.

## Simulation and notification delivery

Every newly established account requires explicit consent and completed **simulated VNeID information-sharing**, except the sole seeded MVP Admin. Driver and Partner registration include it; invited Operators complete it through email activation. Declined/failed simulation cannot be marked complete. Mock information and UI are labelled simulated and make no government-verification claim. Under the [21 October V11-06 clarification](../../05-project-management/decision-log/2026-10-21-vneid-simulation-guid.md), a fake API returns a GUID substitute tied to the user, and User & Access persists that user binding in its database. This GUID is a mock identifier, never a government identity number, identity-assurance proof or authentication credential. The fake API path, property name, remaining mock fields, repeated-call GUID behavior, completion/consent evidence, restricted access, failure shapes and retention remain V11-DES-02 design work. Simulation does not replace contact proof, review, provisioning or MFA. No Admin registration route or MVP role-management endpoint exists.

D10 preserves committed registration, review and provisioning results when notification delivery fails. Persist delivery pending/failed separately; retry the same delivery/business identity without recreating accounts, applications, grants or sites. Queued is not delivered. Existing `GET /api/auth/deliveries/{id}` and `POST /api/auth/deliveries/{id}/retry` require the original authorized actor plus current action/scope; expose metadata only. Exact notification ownership/integration follows [service boundaries](../service-boundaries/ownership-and-events.md), not the old placement of all delivery work in User persistence.

## Discovery and parking products

**Operations owns discovery and accepted availability**; Facility supplies lot identity/location/configuration, Payment supplies authoritative tariff/estimate facts, and IoT supplies raw observations through Operations. The Owner-only `GET /api/parking-lots` listing is not a public discovery API. No new discovery path, query schema or cache lifetime is approved here (V11-DES-08).

| Request context | Required semantics and result facts |
|---|---|
| Origin/radius | Consented current location or manually chosen origin; 5 km default and expansion when empty. Distance uses Haversine ordering and is labelled straight-line distance. |
| Independent filters | Vehicle category and lot type (`outdoor`, `basement`, `multi-storey`), distance, price and availability. Full lots remain labelled unless the availability filter excludes them. |
| No date/time interval | Use current time, backend-confirmed current category availability and current tariff with billing unit. Do not invent duration or total price, or compare unlike hourly/day/night units as one total-price filter. |
| Selected interval | Validate requested vehicle/time interval; show interval availability and Payment-sourced estimated total for price comparison/filtering, with source/freshness. Reservation still revalidates. |
| Selection and booking | Preserve selected lot, vehicle and time context to detail then separate internal 2D/3D booking page. A map marker/model selection grants no hold or reservation. |
| Failure/directions | Distinguish denied GPS, empty results, unavailable MapTiler and stale/disconnected backend facts. Open an external map for directions only; embedded routing/turn-by-turn are excluded. Omit/defer an ETA without an actual source. |

Canonical [discovery SRS](../../01-requirements/srs/modules/03-discovery-visualization.md) and [3D handoff](../../03-design/3d-digital-twin/README.md) preserve physical versus protection state, requested versus allocated location, recorded location precision and stale/reconnect handling.

Monthly/yearly subscriptions are **Driver parking products**, enabled explicitly by an Owner per lot. Price absence/zero is not an enablement flag. Operations owns definitions/coverage and Payment owns financial terms/paid periods/refunds. A yearly period is **12 consecutive calendar months**, with **at most one yearly period in advance**, separate configurable yearly policies and potentially different refund rates. Preserve applicable available-only monthly coverage rules, vehicle/location binding, overlap/dependency guards and money/entitlement separation. Existing monthly three-period prepaid limit and monthly renewal behavior remain unchanged; do not copy them into a new yearly renewal default. V11-DES-05 must settle field schemas, bounds, calendar boundaries and calculations without inventing percentages. See [products SRS](../../01-requirements/srs/modules/07-monthly-passes.md) and [policy catalogue](../../01-requirements/business-rules/policy-catalogue.md).
