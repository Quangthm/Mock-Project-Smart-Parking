## 3. Approved changes

### V11-01 — Partner terminology; existing Owner role

**Approved.** Use Partner Registration for the business onboarding process. Keep the existing Owner role internally; no new Partner role is required.

Update glossary, onboarding narratives, UI terminology and traceability consistently. Do not infer a role-code migration solely from this naming decision.

### V11-02 — Combined first application; document amendments; final outcomes

**Approved.** The initial application combines partner information and the first parking lot. Admin approves or rejects the combined application. These are the only final review outcomes for MVP.

Business discussions and correction requests happen outside SmartPark. The in-system Admin update capability is limited to **uploaded policy/agreement documents**, representing the agreement between the Owner and SmartPark. It does not permit editing other application fields and does not cover pending additional-lot applications.

- Add actual document upload/storage to scope; the earlier FE handoff explicitly did not implement this.
- Admin may replace documents only before approval; finalized approved/rejected applications are immutable.
- Retain the original and each replacement, reason, actor and timestamp.
- On approval after replacement, notify the applicant: **“Your application was approved with some modifications”.**
- This is an approved application with a specific notification, not a third review outcome.
- No in-system request-corrections or applicant re-acceptance workflow is required for MVP. External agreement is not evidence of an in-app consent action.
- Technical design must prevent concurrent changes from silently altering the document version being approved.

### V11-03 — Initial onboarding sequence

**Approved sequence:**

Partner registration → first-lot setup saved → email verification → Admin review/approval → Owner sign-in and use.

Send the email OTP only after setup has been saved. Enforce setup and verified-email prerequisites on the server, not just by disabling FE buttons.

Mandatory VNeID simulation is part of registration under V11-06. Preserve the approved setup-before-email-before-review ordering. Approval must be followed by successful provisioning before normal Owner login; operational opening remains separate.

### V11-04 — Create pending account immediately

**Approved.** Create the account record immediately during registration in a pending/non-operational state, preserving the existing account-creation approach. A normal Owner session is not available before approval.

Keep these concepts separate:
- User/contact verification state;
- Account access/approval state;
- Partner application review state;
- Lot approval/provisioning state;
- Lot operational readiness/open state.

A pending record is a persistent identity to associate with the application and verification challenge; it is not permission to use Owner operations.

**Verified implementation:** see section 4. Current code uses different pending labels on User and Account, so “pending” must not be documented as one universal status.

Restricted setup/verification credentials are approved under D07. Their expiry and secure recovery wire contracts remain technical design tasks, not permission to grant a normal Owner session.

### V11-05 — Independent approval for subsequent lots

**Approved.** An already approved Owner submits a separate lot application for Admin review. Each subsequent lot requires approval; existing Owner approval does not automatically approve future lots.

- Admin approves or rejects the new lot application.
- Rejection leaves the existing Owner account and approved lots unaffected.
- Approved lots become activated/authorized, but are not automatically open for parking.
- Rejected lot applications remain immutable history.
- Provide **Draft as new lot application** to create a new proposal based on a rejected one.
- Do not require comparison with earlier rejected application content or block an identical proposal merely for being identical.
- New drafts/proposals have their own identity and review outcome; they do not reopen or overwrite the rejected record.

No request-corrections workflow is required. Admin document editing under V11-02 does not apply to pending additional-lot applications.

Do not confuse the absence of content-deduplication checks with request retry safety: retrying one submission must not accidentally create several applications/sites.

### V11-06 — Mandatory simulated VNeID; sole seeded-Admin exemption

**Approved.** Simulated VNeID information-sharing is mandatory for every role as part of establishing an account, with **one explicit exception: the single seeded MVP Admin**.

- Driver and Owner complete it as part of registration.
- Invited Operators complete it when following the email activation link. Verified-contact activation is required; setting a password is **optional**, preserving OTP login eligibility.
- MVP has exactly one seeded Admin and **no Admin registration route**. That seeded account requires no VNeID simulation.
- There is no general exemption for Operators or other users. No additional Admin onboarding flow is introduced.
- Simulation does not replace email/contact verification, Owner/lot approval or MFA.
- Clearly label the screen and returned mock information as simulated; do not claim government integration or real identity verification.
- Preserve explicit information-sharing consent. Do not mark a failed or declined mandatory simulation as complete.

Mock fields, completion evidence, retention and failure payloads must be specified in the implementation/API design without inventing production identity assurance.

### V11-07 — Approval, provisioning and operational opening are distinct

**Approved.** Approval authorizes a lot; opening for parking depends on required configuration and readiness.

If provisioning fails after the review decision:
- preserve an explicit pending/failed provisioning state;
- support safe retry;
- do not falsely report onboarding complete;
- do not create duplicate sites;
- do not require the Owner to submit/create the same first lot again after sign-in.

A failed provisioning operation must not be represented as business rejection.

**Approved access rule:** Owner login is blocked while initial provisioning is pending or failed, with an appropriate safe reason. Do not issue a restricted normal Owner session as a workaround. Notify the applicant of approval through email, but distinguish the review decision from readiness to sign in.

Readiness-to-open checks and permissions must be mapped to the existing facility/operations contracts in the documentation update. Approval/activation does not automatically open a lot.

### V11-08 — Development database reset after documentation approval

**Approved direction.** The project is still in development. Reset development databases after the documentation is updated and approved so invalid old data is removed.

This replaces the earlier proposal to migrate/grandfather existing development applications as the selected transition approach.

This task does not execute a reset. Record the target environments, responsible teammate, reset/seed scripts and execution date in the implementation plan. Documentation approval is a prerequisite; resetting data cannot substitute for fixing schema, seed and application incompatibilities.

### V11-09 — Preserve service ownership across the setup form

**Approved.** A combined onboarding form does not change authoritative service ownership.

- User: identity, partner organization/tenant identity, membership and registration/review information.
- Facility: lot configuration, spatial structure and facility readiness configuration.
- Operations: monthly-plan definition/coverage and accepted operational state, consistent with the existing ownership decisions.
- Payment: authoritative tariffs and financial terms.
- IoT: external device integrations and raw observations, with exact device configuration responsibilities reconciled in the interface contract.

The onboarding application may retain the submitted proposal/review evidence, but that is not authority to independently manage another service's operational records.

Update handoff references to legacy Parking Service ownership. Do not implement new external orchestration inside Domain or treat the current repository implementation as an approved architectural pattern.

### V11-10 — Monthly and yearly Driver parking products

**Approved.** These are products sold to Drivers, not an Owner platform subscription. Owners configure whether their lots offer monthly and/or yearly subscriptions.

- A yearly pass covers **12 consecutive calendar months**.
- MVP permits at most **one yearly period purchased in advance**.
- Retain applicable monthly-pass coverage rules, with a separate configurable yearly policy set; monthly and yearly refund rates may differ.
- The yearly period has its own approved advance-purchase limit; do not apply the monthly maximum-three-prepaid-period limit to prohibit the annual product. Existing monthly limits remain unchanged.
- Preserve Operations ownership of plan definition/coverage and Payment ownership of financial terms.
- Express product enablement separately from price; zero/absent prices must not silently stand in for an enablement flag.

Exact configurable policy fields, defaults/bounds, calendar-boundary examples and financial calculations remain documentation/design work. No unapproved refund percentage or renewal behavior is implied.

### V11-11 — Minimal normal login success; preserve meaningful failures

**Approved.** Simplify normal successful login responses to necessary tokens. Do not always include onboarding/profile information. Retrieve relevant authenticated account/profile information separately, such as through /me.

This does **not** authorize removal of meaningful failure codes/reasons or required information from error responses. Keep safe, standardized, actionable errors; do not expose raw exception details or sensitive data.

A required MFA challenge is not a completed normal login. Preserve the approved staged authentication flow rather than issuing a full session before MFA.

Exact response envelope, token delivery contract and error payload schema still require API agreement.

### V11-12 — MapTiler geographic parking discovery and booking handoff

**Approved.** MapTiler provides the geographic parking-discovery map. Internal 2D/3D lot visualization remains a separate page/capability.

Users can:
1. Use consented current location or a manually chosen location as search origin.
2. Search lots, retaining the existing **5 km default radius** and expansion when empty.
3. Compare distance using Haversine ordering; filter by distance, price and availability.
4. Filter vehicle category (for example car/motorcycle) independently from lot type: **outdoor, basement, multi-storey**.
5. See backend-confirmed availability, lot identity/location and pricing; full lots remain visibly labelled unless intentionally excluded by an availability filter.
6. Select a lot to see important details and use a button to open its internal 2D/3D model page for booking.
7. Optionally open an external map for directions.

**Time, availability and price semantics**
- When no date/time is selected, default to **current time**. Show current backend-confirmed availability for the selected vehicle category and the currently applicable tariff with its billing unit.
- Do not invent a parking duration or a total price when none was supplied.
- Once an interval is selected, use availability for that vehicle/interval and estimated total charge for price comparison/filtering.
- Without an interval, display labelled current tariffs; do not compare unlike hourly/day/night tariff units as though they were a single normalized total-price filter.
- Backend confirmation remains required for reservation. A marker, availability count or selected model slot does not reserve capacity.
- Keep price/availability source and freshness meaningful; handle denied GPS, empty results and stale/disconnected data distinctly.

**Directions and scope**
- Embedded route calculation and turn-by-turn navigation are **out of scope**.
- Show a travel estimate only when it has an actual source. Otherwise omit it and explicitly defer that requirement.
- Straight-line Haversine distance must not be labelled road distance or travel time.
- Preserve internal 2D/3D rules: backend authority, physical versus protection state, requested versus allocated location, recorded vehicle-location precision and stale/reconnect handling.

**Implementation evidence — not acceptance**

The inspected FindParking data path used localStorage rather than a backend discovery API. It did not establish full radius, vehicle/time, price/availability filter or live-refresh compliance.
The project lead reports FE filters already exist; the newer branch/commit and end-to-end behavior still require verification. Do not label the feature complete from either statement alone.

Observed call path:
1. AuthController.RegisterOwner delegates POST /api/auth/register/owner to RegisterAsync.
2. OwnerRegistrationService.RegisterAsync constructs a User with PendingVerification, an Account with PENDING_APPROVAL and BUSINESS_OWNER role, and an OwnerApplication linked to the User.
3. It saves these records, issues the Owner email challenge immediately, and commits.
4. AccountWorkflowService.VerifyOwnerAsync (lines 131–143) consumes the valid challenge, records EmailVerifiedAt and changes User status to PendingApproval.
5. OwnerRegistrationService.ReviewAsync requires a pending application, User.PendingApproval, verified email and eligible PENDING_APPROVAL account.
6. Approval sets User Active, provisions a tenant through the existing parking integration, and sets Account ACTIVE. Rejection sets User Rejected and Account INACTIVE.

**Conclusion:** immediate pending account creation is already present. The new requirement preserves that timing but adds first-lot setup, mandatory simulation, deferred OTP issuance, combined approval and separately observable provisioning. Current code is not proof that these new requirements are implemented.

Current source also puts provisioning within the review's local transaction; the new pending/failed provisioning contract needs an explicit implementation design. This inspection does not approve current service placement, ownership, role names or cross-service consistency.

## 8. Proposed verification backlog

These are future acceptance/regression checks, not executed test results.

- Registration persists one pending User/Account/application; a pending identity cannot obtain normal Owner privileges.
- Setup retry preserves application identity and does not duplicate first lots; OTP is not issued before setup completion.
- Mandatory simulation applies to every non-exempt account through registration/activation; the sole seeded Admin is exempt and there is no Admin registration route. Simulation does not bypass verified email or review.
- Admin cannot approve without required setup, verification and simulation evidence.
- Admin edits follow the final allowlist and audit rules; concurrent edit/review cannot approve unseen data.
- Initial approval results in one tenant and first lot; failed/unknown provisioning is observable and retry-safe; onboarding is not falsely complete.
- Additional-lot rejection cannot disable the Owner or affect approved lots.
- Rejected additional-lot application cannot be changed; Draft as new creates a distinct proposal, including when content is identical.
- Approved/activated but unopened lots cannot accept operations that require an open/ready lot.
- Monthly/yearly flags and financial terms follow the final product rules and service ownership.
- Normal successful login omits unnecessary profile/onboarding data; safe error codes/reasons and required MFA challenge data remain.
- Reset/seed setup produces data matching the approved docs and does not silently skip required activation/simulation states.

- Re-enable cannot approve a rejected/pending Owner, restore revoked sessions/grants or clear independent restrictions.
- Single-Admin administrative lock/disable/delete/role changes are rejected; ordinary profile/security and authentication lockouts retain their distinct behavior.
- Rejected initial email cannot register again; additional-lot Draft as new remains available.
- Operator activation works with verified contact and simulation while password setup remains optional.
- Notification failure does not roll back successful approval; delivery retry does not repeat provisioning.
- One invalid member of a same-lot deactivation batch causes no changes to any member; errors identify affected items.
- Vehicle soft removal preserves history and respects active dependencies; cleanup observes retention.
- Annual periods use 12 calendar months and the one-period advance limit; distinct refund policies are applied without changing monthly limits.
- Geographic search uses chosen/current origin, 5 km default/expansion, category and lot-type filters, and backend availability.
- No interval defaults to current time and labelled current tariff; interval selection produces estimated total pricing and interval availability.
- Discovery-to-model-to-booking preserves lot identity and rechecks backend capacity; map selection alone grants nothing.
- External directions work without embedded routing; absent travel-estimate source produces no fabricated ETA.
- Stale map data, unavailable provider, denied location permission and empty search are represented honestly.
