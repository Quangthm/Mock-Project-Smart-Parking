# Operations → Facility durable dependency — inspected pattern and proposed contract

The user directed reuse of Facility's durable slot-management path instead of a persisted full resource projection and subsequently approved a **dedicated Operations credential restricted to the reverse handshake endpoints**. Reviewed the local source on 9 November 2026; no service was run and no Facility implementation was changed. Operations-side durable continuation is in progress. This does not claim the reverse producer already exists.

## Existing path verified in source

### Operations implementation checkpoint — 10 November

The draft now has `ReservationFacilityDependency` in Domain; a dependency repository on the existing ReservationDbContext/UoW; MediatR advance/retry handlers; an independent recovery worker; and a declaration in the original Operations schema. No separate SQL overlay or full structure mirror was added. Unique workflow/purpose identity distinguishes admission from confirmation. The stored snapshot is per-workflow acceptance evidence, not editable Facility configuration.

Booking preparation creates a committed dependency intent before remote acquisition. The dependency worker invokes Facility outside a local database transaction, then locks/reloads the row to persist the response. Local booking hold/confirmation and dependency READY outcome commit together. Terminal preparation fences unused dependencies; ready/completed effects cannot be changed into abort. Recovery continues independently of a completed/expired reservation receipt. Failed work is rescheduled so unavailable tokens do not permanently occupy the first batch.

User binding lookup now also occurs outside a database transaction, serialized by a workflow-specific session guard. It persists one result, with the previously disclosed crash-before-first-commit caveat. Plate and site guards remain transaction scoped; the worker session guard does not reserve capacity.

The owner adapter is explicitly unavailable until Facility delivers matching transport with the approved dedicated Operations credential. No endpoint, header name, credential value or readiness was invented. Capacity evaluation and commercial-effect staging are still unfinished. In particular, Payment acceptance/order/collection calls in the draft progression still require durable staging outside guarded transactions before release. This checkpoint is **not** a completed reservation implementation.

Deploy against both services to verify acquire versus delete, lost acquire/complete/abort replies, restart after local commit, duplicate delivery, and abort tombstones preventing delayed acquisition. Validate that no opposite-direction handshake can create a wait cycle. Existing databases are not upgraded by CREATE IF NOT EXISTS.

## Proposed reverse path for this reservation scope

Use the same durable protocol shape, implemented with **Operations Application MediatR handlers, Domain state and repositories/IUnitOfWork**. Do not copy the legacy store/service workflow arrangement. Producer implementation remains with the Facility teammate.

| Stage | Operations responsibility | Facility owner contract |
|---|---|---|
| Persist intent | After accepted authorization and one-time binding, persist stable token, workflow/purpose, scope, immutable intent fingerprint and pending state before network I/O. Admission acceptance and a later confirmation recheck are distinct effects with stable identities. | No effect requested before this durable intent. |
| Acquire facts/hold | Call outside any Operations DB transaction or held site/plate guard. Same token and payload on every retry. Do not convert timeout/404 into no effect. | Atomically coordinate with slot management; return token-bound immutable site/resource revision, compatible resources and backup facts; retain a durable hold preventing incompatible edits until completion/abort is resolved. Exact replay returns same result; changed payload conflicts. |
| Local acceptance | Under canonical plate then site guards (and Account restriction guard where applicable), reload state; validate policy/terms, restrictions, quota, interval demand and distinct resource usage. Persist accepted facts and local claim/booking plus ready outcome atomically. | The hold must still fence incompatible Facility mutations. Resource facts are used for this workflow; no continuously mirrored catalogue is assumed. |
| Acknowledge local outcome | Outside local transaction, replay the **committed** outcome using the same token. Mark completed only after acknowledgement. Keep request outcome and dependency cleanup independently recoverable. | Complete/release by exact token and fingerprint, idempotently. Subsequent edits use the existing Facility→Operations commitment checks against the newly committed claim. |
| Abort uncommitted work | Fence local preparing work before sending abort. A racing local commit must either win and retain its ready outcome or lose and roll back. Unknown commit is reconciled before choosing abort. | Record token-specific abort/tombstone; a delayed acquire using that token cannot recreate a hold. No site-wide force release based on another request's failure. |
| Recover | Worker reads durable pending rows and dispatches the same MediatR commands. Respect H/T and the approved retry/reconciliation policy. Restart or browser loss cannot erase an uncertain effect. | Query/replay by token distinguishes held, completed, fenced-aborted, in-progress and unknown. Retain evidence beyond transport duplicate windows. |

At confirmation, READY carries reservation ID, confirmation event ID and the accepted evaluation timestamp. It commits atomically with confirmed state, receipt and outbox fact. The [10 November cutoff](../decision-log/2026-11-10-reservation-evaluation-checkpoint.md) requires evaluation strictly before T; commit may finish later. Lost acknowledgement replays the committed outcome, not a new timestamp or effect.

Avoid a cycle between the two protocols: no Operations site guard may be held while waiting on Facility, and Facility must not wait for Operations while holding a local transaction needed by an Operations request. The owner's implementation must show how its existing site gate and new durable dependency hold serialize acquisition versus edits. Incompatible edits may return busy/pending, never silently bypass the hold. Both writers must be deployment-tested together.

## Data and boundaries still required

The durable protocol resolves recovery and mutation races; it does **not** replace missing capacity facts. The owner response needs resource IDs, scope/category compatibility, active/reachable state, fixed/dynamic backup configuration and a revision. Operations combines that with its own claims/visits and quota; aggregate counts alone cannot deduplicate an occupied+protected or occupied+backup slot.

Read-only preview/review can use ordinary versioned queries without taking a hold. Do not keep a Facility edit hold while the Driver fills the form or waits through payment. Release the admission dependency after the local hold claim commits, then acquire a separate dependency when current Facility facts are needed for confirmation/reacquisition. The existing Operations claim is what protects the booking in between.

No full resource mirror, new default, broad force-abort endpoint, shared source project or audit repository is authorized by this inspection. Persist accepted per-workflow facts and durable dependency state only after the refined protocol is agreed. Domain entities belong in Operations Domain, mappings/repository in Persistence, and declarations in the original Operations schema. Audit uses durable outbox events with consumer/retention elsewhere.

**Required before live wiring:** Facility producer delivery and matching versioned acquire/complete/fenced-abort payloads, resource response and transport configuration. The user approved the dedicated Operations credential, but no secret was created/read, no shared key reused, and no arbitrary endpoint/header silently assumed. Use protected transport and service-specific permissions; the producer owner must provision and document them. The earlier full-projection proposal remains unapproved. Source ports and unavailable adapters are not a working lease API; both owners must integrate and verify the protocol.
