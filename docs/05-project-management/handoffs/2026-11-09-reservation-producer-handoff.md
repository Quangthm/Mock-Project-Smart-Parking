## Delivery requested from the Payment teammate

Deliver server-side preview and **versioned accepted-price terms**, combine commercial quote acceptance **inside idempotent `EnsureOrder` (no separate acceptance HTTP call)**, and provide reservation deposit orders with Operations' exact H, verified collection lookup for targeted recovery, durable collection notifications and idempotent reconciliation/refund status. Return a versioned OpenAPI/message schema and setup instructions, including issuer/sender/audience/permissions, paths, RabbitMQ exchanges/queues/ACLs and a sample configured tariff. Do not use browser-supplied amounts or demo payment as authority. Operations owns booking capacity and confirmation; Payment owns money and provider reconciliation. Coverage must be coordinated with its authoritative owner.

The browser displays a server-calculated preview while editing the form, accepts reviewed terms, submits one stable booking intent, and uses the returned order for payment. After payment it resumes the same receipt/own-booking read. Browser redirects and SignalR are notifications only: a paid order is not proof of a confirmed reservation. A hold event may precede order readiness. The UI must wait for an authoritative order and never manufacture one.

Confirmation uses one guarded Operations database evaluation timestamp strictly before T; the transaction may finish later, but confirmation is visible only after commit. Money first verified at/after T cannot create an ordinary reservation. Additional/late collections remain financial obligations even after a booking receipt is terminal.

Keep these three outcomes distinct: payment collected, booking confirmed, refund/reconciliation completed. Publish every distinct verified collection through the Payment transaction's outbox, including collections received after PAID. Replay uses the same event/collection identity; contradictory data for an existing identity is an error.

Reservation-specific implementation must use MediatR handlers, Domain state, repositories and IUnitOfWork; modify only Payment's original schema declarations. Preserve useful provider validation and existing outbox integration. No shared source project, audit repository or invented tariffs/defaults.

## Approved 11 November integration boundary — supersedes older workflow assumptions

**Authoritative decision:** [SPARK-273 event-driven confirmation decision](../decision-log/2026-11-11-reservation-event-driven-confirmation.md) and [cross-team implementation alignment](2026-11-11-SPARK-273-implementation-alignment.md). The November 10 guarded evaluation timestamp and pre-T eligibility cutoff are unchanged; these changes are **not** implemented/tested by publishing this handoff.

- **Creation terminates after the committed Operations `PENDING_PAYMENT` hold.** Operations commits the claim, H, admission outcome and outbox; then a separate durable order-provisioning worker calls Payment *outside* Operations DB transactions. Payment order readiness and driver payment are not conditions for the creation worker to remain active.
- **Combine `AcceptAsync` with `EnsureOrderAsync`** as one idempotent Payment operation after hold commit. Keep the Driver's reviewed immutable commercial terms (`quoteId`/version or equivalent stable snapshot), amount/deposit, validity, selected inputs and coverage evidence. The existing current-tariff calculator is useful, but **recalculating a new tariff after review is not authorization to charge the difference**. Do not interpret the team memo as permission to drop accepted-price binding.
- **Order and checkout are different operations**: Payment returns the single real `orderId` using an authenticated Operations machine request; Driver invokes the existing authenticated payOS checkout for that order. Exact `expiresAt=H`; no new order/checkout at or after H. Retrying an ambiguous order creation may only discover the same order or a durable closed-no-order result.
- **Payment collection is not confirmation**: Payment verifies actual provider evidence and emits a durable event for each distinct collection. A separate Operations consumer confirms with the approved guard/expiry/cutoff semantics. Event replay does not duplicate claims, booking confirmations or refunds; normal per-second payment polling is removed. After terminal booking receipts, late/additional money remains discoverable and reconciled.
- **Facility/claim fast-path gate:** a current valid held claim *may* authorize aggregate-only confirmation after all relevant Operations/Facility/Gate writers prove the live-claim invariant. Until then, retain the existing confirmation Facility dependency and availability/plate/guard checks. Expired/invalidated holds require fresh compatible pre-T reacquisition or financial reconciliation.
- **Coverage ownership:** Payment records immutable covered amount/reference/version but is not the source of pass/discount entitlement. Define a trusted acceptance/cancellation handshake with the actual coverage owner; failure/unknown is not zero-price. Genuine zero-price bookings need authoritative validation and use **no synthetic Payment order**.

**Expected provider contract proposal** (names not yet owner-agreed): `PUT /internal/reservation-deposit-orders/{operationId}`; same-payload replay `CREATED(orderId)`, ambiguous `UNKNOWN`, durably fenced `CLOSED_NO_ORDER`, payload conflict `409`; authenticated collection lookup and idempotent reconciliation acceptance; versioned `ReservationDepositCollectedV1` event with `eventId`, `collectionId`, order/transaction/operation/reservation/account/tenant/site/accepted-terms/amount/currency/provider binding. Dedicated restricted machine JWT for S2S; Driver JWT is for own checkout only. A generic `role=SERVICE` alone is not a sufficient permission contract.

### Open defect — reserved-session exit checkout reference

This affects the parking fee collected at exit for a vehicle that entered on a reservation. It is separate from the deposit collected before arrival.

1. [Operations checkout preparation](../../../src/Services/OperationService/SmartParking.OperationService.Application/Usecase/ReservationGate/ReservationUseCases.cs#L78) finds the active parking session by reservation ID. The [checkout client](../../../src/Services/OperationService/SmartParking.OperationService.Infrastructure/Clients/CheckoutPaymentClient.cs#L63) sends that reservation ID as `sessionId` alongside `referenceType=RESERVATION`.
2. The [Payment prepare endpoint](../../../src/Services/PaymentService/SmartParking.PaymentService.API/Controllers/PaymentsController.cs#L84) forwards `SessionId`. The [order handler](../../../src/Services/PaymentService/SmartParking.PaymentService.Application/Usecase/PrepareParkingFeeOrder/PrepareParkingFeeOrderCommandHandler.cs#L188) stores it as the ID of a `PARKING_SESSION` reference. `PaymentSucceededV1` then carries the stored type and ID.
3. The [Operations consumer workflow](../../../src/Services/OperationService/SmartParking.OperationService.Application/Usecase/ReservationGate/SimulatePaidGateDepartureCommandHandler.cs#L20) resolves a `PARKING_SESSION` reference by session ID before checking the bound checkout order. It receives a reservation ID, so payment can settle while the session remains open and the scanned slot remains occupied.

**Payment and Operations follow-up:** Agree on the reference that identifies the exit checkout target. One option is for Operations to send the actual parking-session ID for every `PARKING_FEE` order. Another is for Payment to accept and preserve a validated `RESERVATION` reference for reserved exit checkout. In either case, keep the stored order and emitted event consistent, and have Operations verify that the paid order is bound to the resolved session. Review outstanding orders with the old reference before changing replay behavior.

**Acceptance evidence:** Exercise reserved and walk-in checkout through cash and payOS. Verify the stored order reference, the published event, and the session resolved by Operations. A matching checkout event should record settlement, trigger simulated departure at the event timestamp, and release the scanned slot. Verify that a booking deposit or an unrelated checkout order leaves the session open and that redelivery preserves the original exit timestamp. Source-reviewed only. Live verification is pending.

### Open gap — live operator refresh after checkout

**Current behavior, source-reviewed:** PaymentService stages `PaymentSucceededV1` in its outbox after cash settlement, including a 0 VND checkout. The [Operations RabbitMQ consumer](../../../src/Services/OperationService/SmartParking.OperationService.Infrastructure/Messaging/PaymentSucceededConsumer.cs#L30) dispatches the [simulated departure command](../../../src/Services/OperationService/SmartParking.OperationService.Application/Usecase/ReservationGate/SimulatePaidGateDepartureCommandHandler.cs#L18). That command commits the session exit and local allocation release, then requests release of the scanned Facility slot. There is no SignalR event wired to that commit for the operator checkout screen. The existing [payment notification consumer](../../../src/Services/NotificationAuditService/SmartParking.NotificationAuditService.Infrastructure/Consumers/PaymentNotificationConsumer.cs#L22) handles payment notifications separately. The existing [operator hub client](../../../FE/src/lib/operatorLive.ts#L27) listens for operator account changes.

**Operator impact:** [Gate Check-Out](../../../FE/src/roles/operator/check-in-out/CheckInOut.tsx#L456) refreshes parking history immediately after the Cash request returns. If RabbitMQ delivery or Operations processing takes longer than that refresh, the table and open record can keep showing `Pending Payment` even after the session closes. Cash checkout has no QR step. Reloading history reads the committed status.

**Operations and Frontend follow-up:** Agree on a SignalR notification for committed session departure, scoped to operators authorized for that tenant and site. Use it to refresh the site's parking sessions from Operations so the table and any open record show the committed status and exit time. Refresh on reconnect to recover missed notifications. Payment's success event remains the financial trigger. The UI should show checkout completion only after Operations confirms departure. Hub ownership, event name, and payload remain open.

**Acceptance evidence:** Delay RabbitMQ delivery after confirming a 0 VND cash checkout. Keep the parking record open and verify it updates to `Completed` with the recorded exit time after Operations commits, without a manual reload. Verify that duplicate notifications are harmless, reconnect recovers a missed update, and operators at another site receive no checkout notification. Live verification is pending.
