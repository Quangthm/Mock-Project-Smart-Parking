# Reservation producers — Payment, Facility and coverage handoff

Reviewed source in the SPARK-273 working tree on 9 November 2026, based on committed baseline `0a2383bdfedf34058c4a2bae99c1ae9087162da0`. This is source review, not live verification. Producer implementations remain with teammates. No Payment or Facility implementation was changed. Operations ports are in [BookingContracts.cs](../../../src/Services/OperationService/SmartParking.OperationService.Application/Reservations/BookingContracts.cs); these service-local C# ports specify required semantics, **not delivered HTTP endpoints or agreed wire authentication**. There is no `src/Shared` build dependency.

## What Operations needs, and why

| Owner operation | Required data and behavior | Purpose |
|---|---|---|
| Price preview | Site/slot/start/end, optional vehicle/method; server-calculated booked amount, applicable deposit when determinable, VND, pricing version, whether complete selection is still needed | Display amount while the user edits the form. Missing configuration must not become zero. Preview creates no booking, claim or order. |
| Versioned reservation quote | Quote ID/version/expiry; exact Account, vehicle, site, slot, UTC interval and method; booked/deposit amounts, currency, FULL/PERCENTAGE/FIXED mode; coverage version and disclosure | Preserve what the Driver actually accepted. Genuine zero price is explicit; positive price with a rounded-to-zero deposit is invalid. FIXED may exceed booked charge under the catalogue. |
| Quote/coverage acceptance | Stable Operations workflow ID; exact accepted quote; durable identical replay, reject changed payload; serialize with relevant tariff/coverage changes | A read followed by a local version comparison cannot prevent a coverage cancellation race. Define release/reconciliation of accepted coverage when local booking creation never commits. |
| Ensure deposit order | Stable operation/workflow ID and reservation ID; Account/tenant/site; quote/terms version; amount/currency/method; **Operations H as expiresAt** | Return the same order after lost acknowledgement, without extending H or recalculating accepted terms. Do not create a fresh order at/after H. |
| Order outcome | `CREATED` with order ID and exact accepted request; `UNKNOWN` with no claimed absence; `CLOSED_NO_ORDER` with a durable fence preventing later creation for that operation | Operations must distinguish an unacknowledged order from proven absence after expiry. A timeout/404 is not proof of no effect. |
| Verified collections | Complete collection identities for the order and their booking/Account/tenant/site/quote/version/amount/currency binding; `PENDING`, `UNKNOWN`, `SETTLED`, or definitive `CLOSED_NO_COLLECTION` | Every distinct collected amount must be accounted for. A paid boolean or the newest transaction alone hides duplicate collections. Contradictory payloads for one identity fail closed. |
| Financial reconciliation acceptance | Idempotent durable acceptance by reservation + collection + reason; observable disposition and payout status | Late or additional money must be reconciled once without granting an expired booking or inventing a second charge. Acceptance is not a completed refund. |
| Durable financial notifications | Owner-authenticated messages for **every** newly verified collection, including after an order is already PAID or Operations has completed/expired its receipt; stable IDs and authenticated lookup/replay | Terminal receipts are not polled by the current worker. Late/additional collections need a consumer and recovery path; this is still an Operations integration gate. Agree versioned wire contract, topology and replay before implementation. |
| Facility acceptance facts | Tenant/site/slot identity, eligible CAR resource, immutable revision, site readiness, and participation by every closure/retirement/configuration writer in the structure handshake | Prevent acceptance against a disappearing/ineligible resource. A `participatesInStructureGuard` boolean is a requirement, not evidence that the owner implemented it. |
| Facility resource projection | Versioned compatible resources, scope/category, fixed/dynamic backup membership and applicable resource configuration, guarded against concurrent structure changes | Operations must evaluate interval demand/quota and union occupied/protected/backup resource identities. Aggregate counters cannot implement distinct-resource accounting. This extension remains to be agreed with Facility. |

Use independently versioned service-local DTOs or published schemas. Do not reference another service's Application/Domain assembly. Operations owns reservation capacity, policies, claims and confirmation; Payment owns authoritative financial terms, orders, provider verification and refunds. Operations coverage ownership must remain consistent with the existing pass/dependency boundary; do not assume Payment can manufacture a coverage guarantee itself. The existing shared-key exception covers only User vehicle lookup. Define other HTTP service identity/permissions and RabbitMQ publisher/consumer ACLs with the owning teams before wiring adapters.

| Same checkout handler | Calls provider before persisting attempt; counts FAILED retries; UNKNOWN does not visibly block a fresh attempt | Persist stable attempt intent before provider effects; reconcile unknown outcomes by the same provider key before another charge. | [GetPaymentStatusQueryHandler](../../../src/Services/PaymentService/SmartParking.PaymentService.Application/Usecase/GetPaymentStatus/GetPaymentStatusQueryHandler.cs) | Loads by transaction ID, no Account authorization in handler; queries provider and can publish success | Enforce caller ownership on user reads and a separate restricted machine lookup. | Webhook handler under `Application/Usecase/ProcessWebhook` | Existing signature validation, webhook deduplication and amount validation are useful; paid-order early acknowledgement and latest-transaction matching need review | Correlate the exact provider attempt; acknowledge duplicate delivery without suppressing a genuinely different collection. | [PaymentSucceededV1](../../../src/Services/PaymentService/SmartParking.PaymentService.Domain/Events/PaymentSucceededV1.cs) | Has order/transaction/Account/scope/amount, but lacks accepted quote/terms version | Supply immutable accepted-version binding in a new compatible contract or restricted authoritative lookup. Operations must not trust an event by matching type name alone. |
| API payment controller | `/orders/prepare` is existing parking-fee preparation, not a versioned reservation quote; Development demo-pay is not provider proof | Deliver reservation-specific producer semantics. Do not connect demo-pay or the existing parking quote as a production substitute. |
| API authentication/composition | Development authentication and production trust differ from Operations local JWKS validation; service URL and messaging settings also differ | Verify real Driver JWT trust, required claims, order ownership, environment-owned service URLs, durable PostgreSQL outbox and restricted broker topology before integration. Configuration alone is not authentication evidence. |

Retain useful existing provider signature checking and EF outbox infrastructure. Fix the actual producer path using direct MediatR handlers, repositories/UoW and Domain state; do not wrap the old handler with a service that silently preserves the unsafe contract. Changes to Payment schemas remain the Payment owner's work in its original script.

## Operations work still required before live sales

The local draft contains review/preview/receipt/own-booking routes, persisted binding, guarded evaluation-time confirmation. Commercial/Facility adapters and capacity acceptance still return explicit unavailable errors. The following are **Operations work**, not delegated Payment fixes:

- Implement guarded interval capacity/quota/protection/backup evaluation from complete resource facts, linked-visit deduplication, expired-hold retirement and cancellation restrictions.
- Move external calls out of guarded database transactions and finish durable stages/replay/compensation for ambiguous owner acceptance. Current draft progression still makes owner calls while holding locks and is not release-ready.
- Integrate the agreed owner transports, collection notifications and post-terminal reconciliation. The current worker only polls open receipts; it cannot discover money arriving after completion by itself.
- Complete bounded readiness, failure handling and deployment evidence. Do not turn unavailable implementations into permissive success to demonstrate a happy path.

## Joint acceptance evidence

Use a deployed isolated environment after owners deliver contracts. Exercise: edited amount/Account/order IDs; changed terms; concurrent same-key orders; lost order response before/after H; provider timeout followed by duplicate checkout; additional collection after PAID; money first verified at/after T; duplicate/out-of-order events; coverage cancellation versus acceptance; slot retirement versus acceptance. Keep payment state, booking entitlement and refund status independently observable. Verify both real paid and genuinely zero-price confirmation, plus checkpoint/commit recovery under crash/restart. Test execution is deferred at the user's request; see [deployment checklist](../../04-testing/reports/SPARK-273-deployment-checklist.md).

Post-confirmation early/wrong-slot charging follows the [recorded financial decisions](../decision-log/2026-11-09-reservation-confirmation-and-arrival.md). Do not seed a fee or an unpaid-balance waiver on the basis of this handoff.
