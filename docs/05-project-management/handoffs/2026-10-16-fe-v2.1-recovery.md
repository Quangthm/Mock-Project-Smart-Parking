## Operator page request flow

1. FE/src/roles/operator/dashboard/OperatorDashboard.tsx calls loadOperatorSites in FE/src/lib/operatorApi.ts.
2. operatorsApi.assignments in FE/src/lib/parkingApi.ts calls User Service GET /api/operators/me. Existing OperatorProvisioningService.AssignmentsAsync checks active account/role/grant and active sites.
3. parkingApi.operatorLayout calls Parking GET /api/parking-lots/{id}/operator-layout. This route was absent on develop; copying only FE/src leaves this request broken.
4. OperatorLayoutService.ReadAsync calls IOperatorSiteAuthorizer, implemented by Infrastructure/OperatorSiteClient.ScopeAsync. The client calls User Service GET /api/operators/site-scope; OperatorsController.SiteScope resolves the current user's assignment.
5. StructureCommitmentsClient.ReadSnapshotAsync calls Reservation POST /internal/structure/{siteId}/snapshot with the configured service key. StructureSafetyService validates scope, then StructureSafetyStore reads the snapshot without creating a hold.
6. PostgresParkingStructureRepository.ReadAsync loads the tenant/site layout using that snapshot and returns the established structure JSON contract.
7. The dashboard independently requests Reservation GET /api/reservations?siteId=... and Parking /api/operator/sites/{siteId}/tickets and /notifications.

The missing route is verified from source. The user's exact browser failure was not reproduced against their database. Other possible remaining causes are service availability, wrong VITE URLs, CORS origin, expired/revoked session, inactive/missing site assignments, mismatched Services:Key, or unreconciled schema. Diagnose the actual failed URL/status before changing authorization or data.

## Known prototype gaps — not approved production behavior

The lead approved retaining the prototype for recovery, not amending the SRS.

- Recognition-driven automatic session entry is not proof of physical arrival. FR-GATE-01/03 require authoritative guards and actual entry separate from a scan/gate command.
- Walk-in session creation without a slot does not establish available physical capacity. Capacity enforcement and concurrent competing entry need completion and database-backed verification.
- Prototype checkout marks the session/reservation completed and releases allocation. FR-GATE-05 requires settled-charge clearance and separately recorded actual departure; this prototype does not complete that workflow. Payment remains authoritative for tariff and settlement.
- Recognition confidence threshold, plate-only handling and large inline photo data remain prototype decisions, not accepted recognition/media requirements.
- Gate retry/race/unknown-outcome behavior, media retention and full tenant/permission coverage require targeted review and real-DB tests.
- Imported gate/operator endpoints still call persistence stores directly, and some external clients/DTOs remain in API/Persistence. Clean Architecture/CQRS/validation-pipeline alignment is unfinished. Existing develop Application/Domain code was not rolled back to accommodate them.
- The dashboard's support/incident/notification stores are prototype contracts; their service ownership and production lifecycle still need alignment. Driver support/local UI caches are not proof of cross-role persisted workflow completion.
- Owner reassignment has no implemented API adapter/endpoint in this baseline. The UI now states it is unavailable rather than calling a missing method.
- Backup claims' internal endpoints are retained from the feature but are not used by the current gate flow, which deliberately does not claim physical slots. Their presence is not evidence of slot/capacity enforcement.
